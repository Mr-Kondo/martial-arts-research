# 問題を記録して再評価する

利用者が記録を依頼した場合だけ[空の報告票](templates/problem-report.md)をfeedback/の新しい案件フォルダへ保存する。通常実行で全文ログを収集しない。3環境とも同じMarkdownを使用する。エディターで新規作成し、既存報告を上書きしない。

依頼例：

```text
今回の問題を、原文を含めず匿名要約でfeedback/case-001/problem-report.mdへ新規保存してください。
期待結果と実結果、出典箇所、比較条件、版と環境、仮説、未確認事項を分けてください。
既存ファイルがあれば別名にしてください。外部送信はしないでください。
```

保存先は対象プロジェクトのルートのfeedback/とする。Gitを使う配置ではプロジェクトルートを作業ディレクトリとし、保存前に`git check-ignore -v feedback/case-001/problem-report.md`で除外、`git ls-files -- feedback/`が空であることを確認する。別の保存先を利用者が選んだ場合も、check-ignoreとls-filesにその実際のパスを指定して確認する。未除外・追跡済み・確認不能なら保存を止める。feedback/の.gitignoreへの追加や追跡解除は利用者の許可後に別途行い、確認後に保存を再開する。スキル配置内へ保存しない。Gitなしの配置でも非公開性が確認できる保存先を選ぶ。

## 匿名化と公開

原文・秘密情報・個人情報・絶対パスは既定で省く。公開資料の箇所または合成資料を使い、共有不能な証拠は「非公開のため省略」とする。匿名化は完全保証ではない。保存依頼から送信・公開の同意を推測しない。公開するときは内容と提供権限を人が確認する。

既存の公開検証記録には端末の絶対パスが残る4ファイルがある。過去の検証の証拠として保持するが、新規の実行記録はfeedback/へ分離する。再公開資料のパスは<project>等へ置換し、過去の原記録を新しい実測として扱わない。

## 回帰ケースへの変換

1. 失敗した規則と期待判定を1つ選ぶ。実資料をコピーせず、同じ条件を持つ架空の対象・数値で置き換える。
2. 合成であることと出自を明記する。元の問題の解決を保証しない。
3. 同じモデル・資料・設定の比較と、単なる機械検証を区別する。
4. 誤った入力が拒否され、正しい入力が通ることを確認する。

小さい例は[feedback-evidence.json](../evals/regressions/feedback-evidence.json)。未取得の資料について根拠なしでsupportedに格上げした誤りを、既存military記録のコピー上で再現する。原記録は書き換えない。次で失敗再現と修正後合格を確認できる。

```sh
python3 -B -m unittest discover -s scripts/tests -p test_package.py
```

これはguardの記録整合性の回帰確認であり、実資料の正しさやモデル回答品質の改善を証明しない。
